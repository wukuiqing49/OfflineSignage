# Android 功能回归测试

## 持久化约定

所有项目数据相对当前项目 Git 根目录定位，不能相对 Skill 安装目录定位。Skill 可放项目 `.agents/skills/` 或个人技能目录；不依赖特定应用、包名、模块、电脑路径或设备序列号。

- `doc/testing/TEST_PLAN.md`：项目环境、功能用例、源码关联、依赖、执行命令、预期与排除项；首次接入时创建，以后按实际变更维护。
- **`doc/testing/TEST_REPORT.md`：固定的最新测试结果文件**，每轮更新，历史通过 Git 保留。
- `doc/testing/TEST_BASELINE.json`：逐用例的有效通过基线，仅在获得真实通过证据后更新。
- 默认临时日志、截图放 `build/functional-test/<run-id>/`，报告保留命令、摘要和证据位置；需要跨电脑保留的脱敏证据复制至 `doc/testing/evidence/<run-id>/`，在报告中链接。

这三个文本文件应可被 Git 跟踪；检查 ignore 规则，若被忽略说明原因并做最小范围例外。不自动提交或 push。不把本机 SDK 路径、账户、签名口令、token 和私人数据写入报告。用户指定输出路径时遵循用户设置并在计划中记录。

创建项目记录时读取并使用 [项目记录模板](assets/project-records.md)。首次接入不得把模板占位值当真实测试结果。

## 环境和首次接入

1. 读取项目 AGENTS.md、构建文件、Wrapper、模块依赖、Manifest、现有测试源码和测试报告。只在相关任务需要时使用项目已有构建/UI/架构 Skill；缺失这些 Skill 不妨碍本流程。
2. 识别实际 Gradle 任务、构建变体、applicationId、测试 runner、JDK/SDK、XML 或 Compose UI。用环境变量或 local.properties 定位 SDK/adb，正确解码 Java properties 路径；Windows 使用 gradlew.bat，其余使用 ./gradlew。
3. 检查 adb devices；多设备时明确目标，所有命令带目标设备参数。记录 Android/API、机型、安装包版本与构建来源。换电脑只重新检查环境；历史设备结果不能冒充当前设备结果。
4. 为每个功能建立稳定用例 ID，记录源码路径、共享依赖、上下游功能、前置数据、操作、可判断的预期、测试方法及命令。用例方法可为 JVM、instrumentation、UI 自动化、人工；缺少自动化时如实记录。
5. 将用户排除项记录为本项目、本轮或长期排除，明确有效范围；不继承其他项目的例外。

## 选择测试

默认增量模式；首次无可靠基线时建立覆盖清单并执行可用基准测试。用户要求发布测试时走发布模式。

- 比较每个用例最近有效基线与 HEAD，并纳入 staged、unstaged、untracked 源码；使用 git diff --name-status 及 git status --porcelain，处理删除、重命名和新文件。基线提交在浅克隆中缺失、分支历史不兼容或依赖不明时扩大范围，并记录原因。
- 分析模块依赖及调用关系，选择直接修改功能和受影响消费者。新增代码或测试不在映射中时更新计划，不能直接跳过。
- 计算/价格规则影响使用它的页面和导出；数据库影响迁移、读写、恢复；共享主题/基础 UI 影响使用页面；Manifest、依赖、签名、R8 影响构建和启动；权限/登录/计费影响状态及功能门禁。
- UI 变更验证相关页面的日夜主题、字体缩放、横竖屏与 Insets；根据实际支持范围选择。仅文档改动一般只检查文档。
- 功能增量测试保留少量项目定义的核心冒烟检查。发布模式增加核心闭环、正式构建安装启动，以及受影响的数据迁移和平台兼容检查；不可把单机结果扩展成所有设备通过。
- 写清每个选中用例的原因，以及未选用例为何不需复测。不可仅比较 HEAD~1，也不能因文件名没变化就忽略上游影响。

## 执行和证据

先执行低成本 JVM/静态检查，再构建与安装、设备端测试、必要的页面操作。使用已确认存在的任务和 runner；不要直接复制别的项目命令。独立检查可并行，共享设备操作串行。

UI 优先 resource-id、可访问性属性或 Compose semantics 定位。使用坐标前读取当前页面和控件边界；每次跳转后核实实际页面，避免对错误窗口继续点击。URL 出现在地址栏仅证明跳转，正文或截图确认内容加载后才能判断页面可用。HTTP 200 不代表页面内容正确。

保护设备已有数据：先检查测试 setup/teardown 是否删除数据库或清理账户；会影响已有数据的测试使用隔离测试包、模拟器或已确认可清空的设备。不得默认 pm clear、卸载或运行清库测试。临时修改字体、方向、主题后恢复原值，清理仅本轮创建的数据。

登录、购买、外发等按用户授权范围执行。真实收费或外发缺少明确对象/授权时停在对应步骤，并继续其他独立检查。用户完成的测试标记“用户确认”，不写成 agent 实测。

逐项记录执行命令、退出码/断言、页面预期与观察、证据、耗时和环境。构建成功不等于功能通过；静态规则扫描不等于视觉验证；测试数量不等于功能覆盖率。请求仅为测试时，发现问题先记录，不自动更改业务逻辑。

## 结果与基线

始终更新固定报告，即使设备离线或部分测试失败。状态只能为：本次通过、失败、受阻、未执行、历史通过未复测、用户确认、排除。报告区分这些数量，结论仅针对本轮范围，不自动给出整体发布保证。

基线按用例维护，包含 commit、源码工作区指纹、环境、变体、时间和证据。只更新本次实测通过的条目；失败、受阻、跳过、用户确认不推进自动通过基线。未提交源码参与测试时不得仅存 HEAD：记录 diff/未跟踪源码内容摘要，排除报告和构建产物；若未实现可靠指纹，该用例基线不推进，下次重新测试。无关用例保留各自旧基线。

最终告知报告路径、执行/失败/受阻数量及剩余项。报告、计划、基线随仓库迁移；大日志留本机，关键证据随 Git 保存。Skill 负责测试编排，无法替代尚不存在的自动化用例。
